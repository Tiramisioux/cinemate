# F-006 — No CI runs on pull requests or on the `dev` branch

- **repo:** cinemate
- **severity:** high
- **confidence:** confirmed
- **category:** test-gap
- **evidence:** `.github/workflows/docs.yml:9-13`, `_test/` (27 pytest files), PR #129 status API returning `total_count: 0`
- **needs-pi:** partly — see PI-002
- **effort:** M

## What

KICKOFF §6.4 states "CI contains only `docs.yml`". True, but it understates the problem.
`docs.yml` is the only workflow **and it does not run on this repo's development branch**:

```
.github/workflows/docs.yml:9    on:
                           10      push:
                           11        branches:
                           12          - main
                           13      workflow_dispatch:
```

There is no `pull_request` trigger and no `dev` trigger. Both repos develop on `dev`
(KICKOFF §3), and `origin/dev` is 26 commits ahead of where local `dev` sat at S01.

**Confirmed empirically:** the GitHub status API for PR #129 (this review's own PR,
targeting `dev`) returns `total_count: 0` — not a failing check, not a skipped check.
Zero checks exist.

So the actual situation is:

| What could run | When it runs today |
|---|---|
| 27 pytest files in `_test/` | **never** — no workflow references them |
| mkdocs build (catches broken nav, missing pages, bad links) | only on push to `main` |
| any lint / format / type check | does not exist (F-005) |

A change can be developed on `dev`, reviewed, and merged with **nothing** having been
verified automatically — including the docs build, which is the one thing the repo does
have tooling for.

## Why it matters

This is the enabling condition for several other findings rather than an isolated gap.
F-004 (five 0-byte docs, 15 pages unreachable from the nav) and F-002/F-003 (two divergent
dependency lists) are precisely the class of defect a cheap CI job catches on the commit
that introduces it. They accumulated because nothing was watching.

It also makes every remediation in this review riskier than it needs to be. S12 will
propose batches of changes; without CI there is no automated signal that a batch broke
something, so each one falls back on manual Pi testing — the scarcest resource in this
project.

## Proposed action

Deliberately minimal, per KICKOFF §8 S06 ("do not propose a twelve-tool pipeline that will
be abandoned"). Two workflow changes, in priority order:

1. **Add `pull_request` and `dev` triggers to the existing docs build.** This is a
   three-line change to a workflow that already works, and it immediately starts catching
   the F-004 class of defect. Highest value per unit of effort in the entire review.
2. **Add a test workflow** running the portable subset of `_test/` on `ubuntu-latest`.

Step 2 is blocked on knowing which tests are portable — several import `gpiozero`,
`sugarpie`, `grove.adc`, `systemd`, which do not install off-Pi. **PI-002 establishes that
split.** Until it runs, S06 should draft the workflow with the assumption stated
explicitly rather than guessing at a marker set.

Note that step 1 is not blocked on anything and could ship independently of this review.

## Risk if changed

Low, and worth stating precisely because it is not zero: adding a `pull_request` trigger
to `docs.yml` as written would run the **full** job on every PR, including the
`peaceiris/actions-gh-pages` deploy step and the "copy PDF and push" step. Those must be
gated (`if: github.event_name == 'push' && github.ref == 'refs/heads/main'`) or a PR build
will deploy the site and push a commit.

That is a real trap, not a hypothetical: the deploy step has `contents: write` and the PDF
step runs `git push`. **Whoever implements this must split build from deploy, not just add
a trigger.**

## How to verify the fix (Mac / Pi)

- **Mac:** open a throwaway PR touching only `docs/`; confirm the build check appears,
  runs, and that `gh-pages` is untouched and no "CI: update rendered PDF" commit lands.
- **Pi:** none for step 1. Step 2 needs PI-002 first.
