# F-016 — The `audio_vu` Redis key is hand-duplicated across the C++/Python repo boundary

- **repo:** both
- **severity:** high
- **confidence:** confirmed
- **category:** redundancy
- **evidence:** `cinepi-raw/cinepi/cinepi_sound.cpp:22`, `cinemate/src/module/simple_gui.py:21`, `simple_gui.py:1166-1172`
- **needs-pi:** no
- **effort:** M

## What

The audio VU meter is a cross-repo contract. cinepi-raw writes the level data to Redis;
cinemate's HDMI GUI reads it. Both sides declare the key independently — **same constant
name, same string value, no shared source of truth:**

```
cinepi-raw/cinepi/cinepi_sound.cpp:22
    constexpr char RECORDER_VU_REDIS_KEY[] = "audio_vu";

cinemate/src/module/simple_gui.py:21
    RECORDER_VU_REDIS_KEY    = "audio_vu"
```

The identical constant *name* on both sides is the tell: this was deliberately mirrored by
hand, exactly as F-007's colour constants were mirrored between `simple_gui.py` and
`template.html`.

The read side compounds it. `simple_gui._get_recorder_vu_levels()` reaches through the
controller to the raw redis client rather than using the normal accessor
(`simple_gui.py:1166-1172`):

```python
client = getattr(self.redis_controller, "r", None)
if client is None:
    return None
raw = client.get(RECORDER_VU_REDIS_KEY)
```

So `audio_vu` is invisible to three of the four places you would look for it: it is not in
`ParameterKey` (F-015), not in `docs/redis-keys.md`, and not routed through
`RedisController.get_value()` or its cache (F-020).

## Why it matters

This is the same defect class as F-007, but worse in one specific way: **F-007's
duplication is at least visible within a single repo and annotated by comments naming the
counterpart.** F-016's is split across two repositories that version independently, with
nothing on either side noting that the other exists.

The failure mode is silent. Rename the key in `cinepi_sound.cpp` and nothing breaks at
build time, nothing breaks at import time, and no test fails (F-006 — nothing runs
anyway). `_get_recorder_vu_levels()` catches the miss and returns `None`, so the VU meter
simply stops drawing. The operator loses an audio-level indicator mid-shoot with no error
anywhere — a direct violation of KICKOFF §9 principle 3, "fail visible, never silent."

This also makes `audio_vu` the concrete example to cite in ADR-001. The GUI harmonization
question is usually framed as Python-vs-CSS, but the state contract genuinely spans
**three** languages: C++ writes it, Python reads it, and the web GUI needs the same value.
Any shared-token or shared-spec option (§7 options B and C) has to answer for the C++ side,
not just the two Python/HTML surfaces.

## Proposed action

Do not fix this in isolation — fold it into ADR-001's scope, because the answer is the same
mechanism that answers F-007.

The shape of the fix: one machine-readable key registry that both repos consume, rather
than a Python enum and a scatter of C++ `constexpr`s. `ParameterKey` is already 84 members
and is the de-facto registry (F-015); the question is whether it can be generated from, or
generate, a language-neutral source.

Two cheaper interim steps that do not require settling ADR-001:

1. Add `AUDIO_VU = "audio_vu"` to `ParameterKey` and route the read through it. Removes the
   Python-side orphan even while the C++ duplication stands.
2. Add a comment on each side naming the other, matching the convention `template.html`
   already uses for the colour constants. Costs nothing and makes the coupling greppable.

Step 1 alone would also fix F-020 for this key.

## Risk if changed

Low for the interim steps — step 1 is a constant relocation with one call-site change, and
the read path is already defensive.

Non-trivial for the full registry: any generated-header scheme couples the two repos'
build processes, which currently have no relationship at all. That coupling is a real cost
and must be argued in ADR-001, not assumed.

Note the asymmetry that makes any shared scheme awkward: this session can read cinepi-raw
but cannot push to it (STATE.md D2), and the two repos are not versioned together.

## How to verify the fix (Mac / Pi)

- **Mac:** a grep-based consistency check — extract the string literals both sides
  associate with `RECORDER_VU_REDIS_KEY` and assert equality. This is a good first
  candidate for the `harness/` directory and for the CI job proposed in F-006, because it
  needs no hardware and no running camera.
- **Pi:** confirm the VU meter still renders during an audio-armed take. Queued as PI-006 —
  it is the only way to prove the contract end to end, since nothing else exercises it.
