# F-027 — Eleven Redis keys cinepi-raw handles are never referenced by cinemate

- **repo:** both
- **severity:** high (reclassified, not downgraded — see PI-008 update below)
- **confidence:** confirmed
- **category:** correctness (was `redundancy` — reclassified by PI-008)
- **evidence:** `cinepi-raw/cinepi/cinepi_state.hpp:23-52`, `cinepi-raw/cinepi/cinepi_controller.cpp:354,409,444,503,572,577`, `cinemate/src/module/redis_controller.py:18-113`
- **needs-pi:** partly — see PI-008
- **effort:** M

## PI-008 update (2026-08-24)

The static claim is untouched: these 12 key strings genuinely have zero references in
cinemate's source. **The inference this finding drew from that — that the keys are
therefore dead/vestigial — does not hold.** A full boot→record→resolution-change→shutdown
`redis-cli MONITOR` trace (21918 lines) showed every one of the 11 concerns is live:

- **Group A's 6 pub/sub control handlers are still, specifically, never triggered** — the
  MONITOR trace shows no `PUBLISH` on `cp_controls` for any of `awb`/`shutter_s`/`compress`/
  `thumbnail`/`thumbnail_size`/`raw_crop`. That half of "Important qualification" below is
  unaffected: cinemate genuinely never publishes to these channels.
- **But 8 of the 12 strings — the 6 group-A names plus both group-B PLL gains
  (`pll_kp`, `pll_ki`, `pll_deadband_us` minus one already counted) — are read by cinepi-raw
  itself via plain `GET`, exactly once per process (re)start**, with real non-default-looking
  values already resident (`thumbnail=3`, `thumbnail_size=50`, `awb=1`, `compress=0`,
  `shutter_s=56`, `pll_kp=0.06`, `pll_ki=0.0015`, `pll_deadband_us=6.0`). Nothing in the trace
  `SET` them — they were seeded once, long before this session, and persist via Redis's RDB
  snapshot. This is a **separate access pattern from the pub/sub handler table**: cinepi-raw
  treats Redis as its own persistent launch-config store, independent of cinemate's
  `settings.jsonc`, with no source-tracked writer anywhere in either repo.
- **Group C's telemetry (`pll_phase_err_us`, `pll_req_dur_us`) is not dead either — it is
  the opposite of dead.** Both are `SET` ~1401 times each in a 60s window (~every frame at
  25fps, matching `fps_phase_lock=1` on this unit), a real, continuous, unconditional cost
  with zero reader anywhere.

**Net correction:** "6 control handlers that can never fire" (Group A, below) should be read
as "6 pub/sub handlers that can never fire, whose key names ALSO double as an undocumented
launch-config contract cinepi-raw reads from Redis at every startup" — a materially different
and more concerning shape than dead code. Severity stays `high`: an undocumented live
contract with no source-tracked writer is arguably worse than the dead-code framing this
finding started with, per the reconciliation's own worked example.

## What

The two repos keep independent key registries (F-028): cinemate has the 84-member
`ParameterKey` enum; cinepi-raw has 24 `#define CONTROL_KEY_*` macros in
`cinepi_state.hpp:23-52`, dispatched through a handler map on the `cp_controls` pub/sub
channel (`cinepi_controller.cpp:353-676`).

Diffing them: **19 keys are genuinely shared**, and **12 key strings on the C++ side have
zero references anywhere in cinemate** — searched across `src/` and `services/`, `.py` and
`.html`, excluding comments.

Twelve *strings*, eleven *concerns*: `raw_crop` and `rawCrop` are both keys serving one
feature (the first is the pub/sub message name, the second the hash the handler reads with
`hgetall`). An earlier revision of this finding said "11 keys", conflating the two counts.
The reproducible figure is 12 strings, and `harness/redis_key_diff.py` prints it.

They fall into three groups.

### A. Control handlers registered on keys cinemate never publishes (6)

| Key | C++ macro | Handler | What it would do |
|---|---|---|---|
| `awb` | `CONTROL_KEY_WB` (`cinepi_state.hpp:25`) | `cinepi_controller.cpp:409` | sets `libcamera::controls::AwbEnable` |
| `shutter_s` | `CONTROL_KEY_SHUTTER_SPEED` (`:28`) | `:444` | shutter in seconds |
| `compress` | `CONTROL_KEY_COMPRESSION` (`:38`) | `:503` | DNG compression |
| `thumbnail` | `CONTROL_KEY_THUMBNAIL` (`:39`) | `:572` | thumbnail on/off |
| `thumbnail_size` | `CONTROL_KEY_THUMBNAIL_SIZE` (`:40`) | `:577` | thumbnail dimensions |
| `raw_crop` / `rawCrop` | `CONTROL_KEY_RAW_CROP` (`:42`) | `:354` (hash, via `hgetall`) | sensor crop offsets |

These handlers are wired and correct-looking. They simply cannot fire, because the only
publisher on `cp_controls` is cinemate's `RedisController.set_value()`
(`redis_controller.py:229`), and cinemate has no key with any of these names.

**`awb` is the clearest case.** cinemate's white balance is `wb` / `wb_user`
(`ParameterKey.WB`, `WB_USER`), and the actual colour path to the camera goes through
`cg_rb` (`CONTROL_KEY_COLORGAINS`), which *is* shared, plus `--awb auto --awbgains` passed
as launch arguments (`cinepi_multi.py:478-479`). So the `awb` handler is a vestigial
second path to a job already done another way. The near-miss between `wb` and `awb` is
what makes it worth flagging loudly — it reads like a working control and is not one.

### B. Tuning knobs read by C++, never set by cinemate (3)

`pll_kp`, `pll_ki`, `pll_deadband_us` — the phase-lock loop's gains and deadband
(`cinepi_state.hpp:50-52`). cinepi-raw reads them; cinemate never writes them, so they
always take their compiled-in defaults.

### C. Telemetry written by C++, read by nobody (2)

`pll_phase_err_us`, `pll_req_dur_us` (`cinepi_controller.cpp:740-741`) — written every
phase-lock update. Nothing in cinemate reads them, they are not in `ParameterKey`, and
they are not in `docs/redis-keys.md`.

Note also that `sync()` (`cinepi_controller.cpp:87-137`) writes several group-A keys back
to Redis (`shutter_s`, `awb`, `compress`, `thumbnail`), so cinepi-raw is publishing state
that no consumer reads.

## Why it matters

Three distinct costs, and it is worth keeping them separate because they call for
different responses.

1. **Group A is a correctness trap.** Six controls look implemented from the C++ side. A
   developer adding "compression toggle" or "raw crop" support to the GUI would
   reasonably write to `compress` or `raw_crop`, find nothing happens, and have no way to
   tell whether the bug is theirs — because the handler genuinely exists and genuinely
   works, it is just listening on a channel nobody speaks. This is the most expensive
   kind of dead code: the kind that looks alive.

2. **Group B silently disables tuning.** The PLL gains are exposed as if they were
   configurable and are not reachable from anything the operator can touch — not
   `settings.jsonc`, not the CLI, not the web API. Phase-lock behaviour is therefore
   fixed at its defaults on every camera, which may or may not be intended.

3. **Group C is wasted writes on the record path.** `updatePhaseLock` writes two keys per
   update with no reader.

The meta-point matters more than any individual key: **there is no mechanism that would
have caught any of this.** Two registries, two languages, two repos, no shared source
(F-028), no test, no CI (F-006). The keys drifted apart silently and stayed that way.

## Important qualification

"Never referenced by cinemate" is **not** the same as "dead". These keys are reachable
with `redis-cli` by hand, and groups B and C in particular read like a deliberate
debug/tuning surface — you would set `pll_kp` manually while tuning phase lock and watch
`pll_phase_err_us` to see the effect. That is a legitimate design, just an undocumented
one.

So the finding is precisely: **these keys are not part of the cinemate↔cinepi-raw
contract, and nothing says so.** Whether each is vestigial or an intentional manual
surface is a question for the operator, not something the code answers. **PI-008 answered
it (see the update above): not vestigial — an undocumented launch-config contract (groups
A/B) plus live, unread, per-frame telemetry (group C).**

## Proposed action

Do not delete anything on this finding alone — ask first, per group.

1. **Group A:** for each of the six, decide *wire it up* or *remove it*. `awb` is the
   strongest removal candidate (superseded by `cg_rb` + launch args). `raw_crop`,
   `compress` and `thumbnail*` may be features someone wants and never finished — that is
   the operator's call, not the review's.
2. **Group B/C:** if they are a deliberate tuning surface, document them in
   `docs/redis-keys.md` with a "manual/debug only, not written by CineMate" marker. That
   costs one table section and converts a mystery into a feature.
3. **Structural fix (F-028):** whatever ADR-001 concludes about shared tokens should cover
   the key registry too. A generated header or a shared data file would have made this
   diff a build error instead of a review finding.

### Operator decision (2026-08-25)

**Keep all 11 concerns — do not delete.** The operator's own call on point 1 above: these
are candidates for future cinemate-side implementation, not dead surface to prune. This
settles the "ask first, per group" question this finding always deferred — no B2-style
deletion pass should touch any of the 12 key strings in this finding. Point 2 (document the
undocumented contract in `docs/redis-keys.md`) and point 3 (structural fix via ADR-001)
remain live recommendations; only the "or remove it" branch of point 1 is now closed.

## Risk if changed

Removing a group-A handler is low-risk *in cinepi-raw* — the code is unreachable from
cinemate. But it is not zero-risk overall: if anyone drives these keys with `redis-cli`
in a workflow, removal breaks that silently. Confirm with the operator before deleting.

Wiring one up is a behaviour change on the record path and needs Pi validation.
